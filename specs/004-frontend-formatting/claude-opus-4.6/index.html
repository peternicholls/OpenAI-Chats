Decision 1

Transcript Typography & Markdown Readability

The single most impactful design choice in this sprint. Every conversation is a long-form reading experience. Typography density, code block treatment, and heading scale set the tone for the entire product. The spec says "comparably readable and polished" to ChatGPT — but the archive is a reading tool, not a chat tool, which may argue for more generous line height and quieter visual structure.

Key Differences

The Erdős–Graham conjecture was resolved in 2003 by Croot. The proof uses a probabilistic method with the following identity:

∏i Bmi = ∏j Bnj

Here's the helper function that tests primality:

def is_prime(n: int) -> bool:
    if n < 2:
        return False
    for i in range(2, int(n**0.5) + 1):
        if n % i == 0:
            return False
    return True

Note that this is O(√n) which suffices for small values. For a list of related conjectures, see:

  • Goldbach's conjecture — still open
  • Twin prime conjecture — partial results via Zhang
Rationale: Mirrors ChatGPT's own density. 13.5px body, tight leading (1.55), compact code blocks. Familiar to anyone coming from ChatGPT. Maximises visible content per scroll — good for skimming.
Pros
Familiar density; fast scanning of long conversations; less "page" feel
Cons
Can feel cramped for extended reading; headings don't breathe enough; code competes with prose

Decision 3

Date Separators & Conversation Header

Multi-day conversations need orientation cues. The spec references iMessage/Slack patterns: a centred date label between messages when the calendar date changes. The header also needs rework — show start date only (no time), add "Updated [date]" when different, and fix the message count to reflect only visible messages.

Decision 4

Attachments, Fallbacks & Image Modal

Three related presentation questions: (1) How should the fallback block look when structured content can't be rendered? (2) How should image thumbnails sit within the message flow? (3) How polished should the image modal feel? The existing FallbackBlock uses amber/warning colours — is that the right tone, or is "neutral info" more appropriate since this isn't an error but rather unavailable content?

Decision Matrix

Quick reference for all design choices surfaced by this sprint. "Rec" marks the recommended direction based on spec language, existing patterns, and design system consistency.

Decision Area Direction A Direction B Direction C Notes
1. Typography Tight / ChatGPT-native Rec Spacious / Reader — Start tight, loosen after real data review
1b. Code blocks Plain dark Labelled header Rec — Language label + copy is high-value polish
2. ThinkingBlock Minimal / muted Rec Bordered disclosure Tinted accent Minimal collapsed + bordered expanded hybrid
3. Date separator Whisper line Rec Bold label Floating badge Spec says "subtle"; badge is viable fallback
3b. Header Single direction — spec-mandated changes (date-only, updated date, corrected count) Implementation, not design choice
4. Fallback block Warm amber (errors) Neutral grey (known) Rec — Two-tier: neutral for US2, amber for US3
4b. Image modal Already implemented and spec-compliant — dark backdrop is the safe default No change needed
Overall design posture: This sprint's changes should feel like a natural, quiet upgrade to the existing UI. The app already has a clean, utilitarian shadcn/ui foundation. Formatting improvements should make conversations more readable without making the interface feel heavier or more complex. The user came here to re-read conversations — every design choice should serve that goal.
